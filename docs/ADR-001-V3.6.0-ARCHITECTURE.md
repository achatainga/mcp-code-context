# ADR-001: v3.7.0 Architecture Decisions

**Status**: Accepted  
**Date**: May 1, 2026  
**Deciders**: Core team + External review  
**Confidence**: 0.95

---

## Context

mcp-code-context v3.7.0 suffered from critical architectural flaws identified through adversarial analysis and AST-based code review. This ADR documents all architectural decisions for v3.7.0 redesign.

---

## Decision Drivers

1. **Multi-process safety** — Multiple MCP clients must not corrupt files
2. **Zero Native Dependencies** — Maintain plug & play installation promise
3. **Production readiness** — 80%+ test coverage, structured logging, monitoring
4. **Performance** — 10× faster with persistent caching
5. **Developer experience** — Advanced search, token optimization, clear error messages

---

## Decisions

### ADR-001.1: File Locking Strategy

**Status**: Accepted

#### Problem
In-memory locks (`Map<string, boolean>`) don't work across processes. Two MCP clients can simultaneously write to same file, causing corruption.

**Evidence**:
```typescript
// src/utils/fileLock.ts (v3.7.0)
const locks = new Map<string, boolean>(); // ← Only protects THIS process
```

#### Options Considered

| Option | Pros | Cons | Verdict |
|--------|------|------|---------|
| **proper-lockfile** | Cross-platform, stale detection, 2M+ downloads | +1 dependency | ✅ CHOSEN |
| Manual fs.open O_EXCL | Zero dependencies | Not cross-platform, no stale detection | ❌ |
| Redis/external store | Robust | Requires external service | ❌ |

#### Decision
Use `proper-lockfile` with filesystem-based locks in OS temp directory.

**Implementation**:
```typescript
// Locks stored in os.tmpdir()/mcp-locks-{projectHash}/
await lockfile.lock(filePath, {
  stale: 30000, // 30s timeout for stale lock detection
  retries: { retries: 10, minTimeout: 100, maxTimeout: 1000, factor: 2 }
});
```

**Consequences**:
- ✅ Multi-process safe
- ✅ Stale lock recovery
- ✅ Cross-platform
- ⚠️ +1 dependency (acceptable, pure JS)

### ADR-001.2: Backup Storage Location

**Status**: Accepted

#### Problem
Backups in project root (`.mcp-backups/`) trigger infinite loops in hot-reload tools (Vite, Webpack, Nodemon).

**Evidence**: Vite watches all files in project root, including `.mcp-backups/`, causing reload on every backup.

#### Options Considered

| Option | Pros | Cons | Verdict |
|--------|------|------|---------|
| **OS temp directory** | No hot-reload interference, OS auto-cleanup | May be deleted by OS | ✅ CHOSEN |
| Project root with .gitignore | Simple | Hot-reload loops | ❌ |
| User home directory | Persistent | Pollutes user space | ❌ |
| No backups (rely on Git) | Zero overhead | No protection for uncommitted work | ❌ |

#### Decision
Store backups in `os.tmpdir()/mcp-backups-{projectHash}/` with graceful recovery when OS cleans temp directory.

**Implementation**:
```typescript
// Graceful recovery
if (!existsSync(this.backupRoot)) {
  mkdirSync(this.backupRoot, { recursive: true });
}
```

**Consequences**:
- ✅ No hot-reload interference
- ✅ Isolated per project (hash-based)
- ⚠️ May be deleted by OS (mitigated with recovery)

### ADR-001.3: Diff Algorithm

**Status**: Accepted

#### Problem
Custom LCS algorithm O(n×m) space complexity causes OOM on files >5000 lines.

**Evidence**:
```typescript
// src/utils/diff.ts (v3.7.0)
const dp: number[][] = Array(m + 1).fill(null).map(() => Array(n + 1).fill(0));
// For 5000×5000 file: 25 million integers = ~100MB
```

#### Options Considered

| Option | Pros | Cons | Verdict |
|--------|------|------|---------|
| **diff-match-patch** | Google-proven, O(n+d²), 1M+ downloads | +1 dependency | ✅ CHOSEN |
| Custom Myers algorithm | Zero dependencies | Complex implementation, error-prone | ❌ |
| Keep LCS with limit | Simple | Still OOM on large files | ❌ |

#### Decision
Use `diff-match-patch` (Google's implementation of Myers algorithm) with semantic cleanup.

**Implementation**:
```typescript
const dmp = new DiffMatchPatch();
const diffs = dmp.diff_main(oldText, newText);
dmp.diff_cleanupSemantic(diffs);
```

**Consequences**:
- ✅ No OOM on large files
- ✅ O(n+d²) complexity
- ✅ Semantic cleanup (better diffs)
- ⚠️ +1 dependency (acceptable, pure JS)

### ADR-001.4: Persistent Cache Technology

**Status**: Accepted

#### Problem
No caching in v3.7.0. Every operation re-parses files with Tree-sitter (~200-500ms per file).

#### Options Considered

| Option | Pros | Cons | Verdict |
|--------|------|------|---------|
| **sql.js (WASM SQLite)** | Zero native deps, SQL power, 500K+ downloads | ~2MB bundle, slower than native | ✅ CHOSEN |
| better-sqlite3 | Fastest (~50ms) | **BREAKS Zero Native Dependencies** | ❌ REJECTED |
| lowdb (JSON) | Simple, zero deps | Slow on large datasets, no indexing | ❌ |
| In-memory Map | Fast | Lost on restart, no persistence | ❌ |

#### Decision
Use `sql.js` (SQLite compiled to WASM) to maintain Zero Native Dependencies architectural promise.

**Critical Reasoning**:
> "better-sqlite3 requires node-gyp + Python + Visual Studio/GCC during npm install. This would destroy the plug & play installation promise made in CHANGELOG v3.0.6."

**Implementation**:
```typescript
// Debounced save to avoid blocking event loop
class CacheManager {
  private persistTimer: NodeJS.Timeout | null = null;
  
  set(file: CachedFile): void {
    this.db.run(/* INSERT */);
    
    // Debounce persist (Gotcha #4 mitigation)
    if (this.persistTimer) clearTimeout(this.persistTimer);
    this.persistTimer = setTimeout(() => this.persist(), 5000);
  }
  
  private persist(): void {
    const data = this.db.export(); // WASM → Uint8Array
    writeFileSync(this.dbPath, Buffer.from(data));
  }
}
```

**Consequences**:
- ✅ Maintains Zero Native Dependencies
- ✅ SQL power (indexes, queries)
- ✅ 10× faster on cache hit (~80ms vs ~500ms)
- ⚠️ ~2MB bundle size (WASM binary)
- ⚠️ Requires debounced save (mitigated)

### ADR-001.5: Search Tool Strategy

**Status**: Accepted

#### Problem
Manual regex search in Node.js is 10-100× slower than native tools (ripgrep, ag, grep).

**Inspiration**: code-index-mcp

#### Options Considered

| Option | Pros | Cons | Verdict |
|--------|------|------|---------|
| **Auto-detect cascade** | Uses best available tool, graceful fallback | Requires tool detection | ✅ CHOSEN |
| Require ripgrep | Fastest | Breaks on systems without ripgrep | ❌ |
| Pure Node.js regex | Zero dependencies | 10-100× slower | ❌ |

#### Decision
Auto-detect search tools in order of preference: `ripgrep` > `ugrep` > `ag` > `findstr` (Windows) / `grep` (Unix).

**Implementation**:
```typescript
// Platform-aware fallback
const tools = [
  { name: 'ripgrep', command: 'rg' },
  { name: 'ugrep', command: 'ugrep' },
  { name: 'ag', command: 'ag' },
];

if (process.platform === 'win32') {
  tools.push({ name: 'findstr', command: 'findstr' }); // Windows native
} else {
  tools.push({ name: 'grep', command: 'grep' }); // Unix native
}

// Use spawn instead of exec (Gotcha #5 mitigation)
const child = spawn(tool, [pattern, rootDir]);
const rl = readline.createInterface({ input: child.stdout });
for await (const line of rl) {
  results.push(line);
  if (results.length >= maxResults) {
    child.kill(); // Stop after maxResults
    break;
  }
}
```

**Consequences**:
- ✅ 10-100× faster search
- ✅ Cross-platform (Windows/Unix fallbacks)
- ✅ Graceful degradation
- ⚠️ Requires tool detection on startup

### ADR-001.6: Testing Framework

**Status**: Accepted

#### Problem
No automated tests in v3.7.0. All testing done manually with `console.log` assertions.

#### Options Considered

| Option | Pros | Cons | Verdict |
|--------|------|------|---------|
| **Vitest** | Fast, ESM-native, Vite ecosystem | Less mature than Jest | ✅ CHOSEN |
| Jest | Mature, large ecosystem | Slow, ESM issues | ❌ |
| Mocha + Chai | Flexible | Requires more setup | ❌ |

#### Decision
Use Vitest with V8 coverage provider, 80% thresholds.

**Consequences**:
- ✅ Fast test execution
- ✅ ESM-native (no config hacks)
- ✅ Built-in coverage
- ⚠️ Less mature than Jest (acceptable)

### ADR-001.7: Logging Strategy

**Status**: Accepted

#### Problem
`console.log/error` scattered throughout codebase. No structured logging, no log levels, interferes with MCP stdio.

#### Options Considered

| Option | Pros | Cons | Verdict |
|--------|------|------|---------|
| **pino** | Fastest, JSON-native, 5M+ downloads | Fewer features than winston | ✅ CHOSEN |
| winston | Feature-rich, transports | Slower | ❌ |
| bunyan | JSON-native | Less maintained | ❌ |

#### Decision
Use `pino` with stderr stream (MCP-safe), pretty print in development, JSON in production.

**Implementation**:
```typescript
// Logs to stderr (doesn't interfere with MCP stdio on stdout)
class StderrStream extends Transform {
  _transform(chunk: any, encoding: string, callback: Function) {
    process.stderr.write(chunk);
    callback();
  }
}

const logger = pino(baseConfig, new StderrStream());
```

**Consequences**:
- ✅ Structured logging
- ✅ Doesn't interfere with MCP stdio
- ✅ Fast (low overhead)
- ⚠️ Fewer features than winston (acceptable)

### ADR-001.8: File Watcher Technology

**Status**: Accepted

#### Problem
No auto-refresh in v3.7.0. Cache becomes stale when files change externally.

#### Options Considered

| Option | Pros | Cons | Verdict |
|--------|------|------|---------|
| **chokidar** | Cross-platform, stable, 20M+ downloads | Optional native deps (fsevents) | ✅ CHOSEN |
| node:fs.watch | Native | Inconsistent across OS | ❌ |
| watchman | Very fast | Requires external daemon | ❌ |

#### Decision
Use `chokidar` with optional native dependencies (has JS fallback).

**Consequences**:
- ✅ Cross-platform
- ✅ Stable (used by Vite, Webpack)
- ✅ Optional native deps (doesn't break Zero Native Dependencies)
- ⚠️ Slightly slower than watchman (acceptable)

## Rejected Alternatives

### Rejected: Command Pattern Refactor of index.ts

**Claim**: "index.ts is a God Object with 604 lines"

**Analysis**: AST analysis revealed:
- Only 1/16 functions >50 lines (`handleTwoPhaseWrite`: 57 lines)
- Remaining functions are small and focused
- It's an orchestrator, not a God Object

**Decision**: REJECT refactor. Not a real problem.

**Consequences**:
- ✅ Saves 16 hours of unnecessary work
- ✅ Maintains simplicity

---

### Rejected: Migrate to Rust

**Claim**: "Rewrite in Rust for 10× performance and 10× less RAM"

**Analysis**:
- ❌ 3-6 months rewrite time
- ❌ Loses npm ecosystem (Tree-sitter WASM, etc.)
- ❌ Higher barrier for contributors
- ❌ Marginal benefit (Node.js is fast enough)

**Decision**: REJECT migration. Optimize TypeScript/Node.js instead.

**Consequences**:
- ✅ Maintains TypeScript ecosystem
- ✅ Lower barrier for contributors
- ✅ Faster time to market

---

### Rejected: Remove Backup System (Rely on Git)

**Claim**: "Why implement version control when 99.9% use Git?"

**Analysis**:
- Git doesn't protect uncommitted work
- Not all projects use Git
- `rollback_file` is faster than `git checkout`
- 5 versions per file (granular)

**Decision**: REJECT removal. Maintain backup system, improve location (OS temp).

**Consequences**:
- ✅ Protects uncommitted work
- ✅ Fast rollback
- ✅ Works without Git

---

### Rejected: Stateless Mode (No Confirmations)

**Claim**: "Confirmations in memory are lost on restart"

**Analysis**:
- This is **by design** (security)
- Tokens have 5-minute TTL
- Alternative (client stores diff) breaks API

**Decision**: REJECT stateless mode for v3.7.0. Consider for v3.7.0.

**Consequences**:
- ✅ Maintains security
- ✅ No breaking changes
- ⚠️ Tokens lost on restart (documented)

## Architectural Principles

### 1. Zero Native Dependencies
**Rationale**: Plug & play installation on Windows/Mac/Linux without compilers.

**Enforcement**:
- ✅ Use WASM (Tree-sitter, SQLite)
- ✅ Use pure JS libraries
- ✅ Optional native deps OK if JS fallback exists (chokidar)
- ❌ NEVER require node-gyp, Python, Visual Studio, GCC

### 2. Multi-Process Safety
**Rationale**: Multiple MCP clients must not corrupt files.

**Enforcement**:
- ✅ Filesystem-based locks
- ✅ Atomic file writes
- ✅ Tests for concurrent operations
- ❌ NO in-memory shared state

### 3. Production Readiness
**Rationale**: Must be reliable enough for daily use.

**Enforcement**:
- ✅ 80%+ test coverage
- ✅ Structured logging
- ✅ Error recovery (OS temp cleanup, stale locks)
- ✅ Performance benchmarks
- ❌ NO untested code in production

### 4. Developer Experience
**Rationale**: Must be fast and intuitive.

**Enforcement**:
- ✅ <100ms cache hits
- ✅ Advanced search (fuzzy, auto-detect tools)
- ✅ Token optimization (50-80% savings)
- ✅ Clear error messages
- ❌ NO verbose output

## Consequences

### Positive
- ✅ Multi-process safe (no file corruption)
- ✅ Production-ready (80%+ coverage, logging, monitoring)
- ✅ 10× faster (persistent caching)
- ✅ 50-80% token savings (compact diffs, no repetition)
- ✅ Maintains Zero Native Dependencies
- ✅ Zero breaking changes (fully backward compatible)

### Negative
- ⚠️ +6 dependencies (~3MB bundle increase)
- ⚠️ +144 hours implementation time
- ⚠️ sql.js ~30ms slower than better-sqlite3 (acceptable)

### Risks
- ⚠️ OS may delete temp directory (mitigated with recovery)
- ⚠️ Stale locks if SIGKILL (mitigated with 30s timeout)
- ⚠️ Worker memory leaks (mitigated with recycling)
- ⚠️ sql.js I/O blocking (mitigated with debounced save)
- ⚠️ execAsync buffer overflow (mitigated with spawn)
